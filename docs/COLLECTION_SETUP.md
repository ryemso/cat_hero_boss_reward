# 자동 수집 구현 및 운영 설정

2026-10-02 기준. GitHub Pages 웹판의 새 이미지 정산 기록에 적용한다. 설치형은 기존 로컬 정산을 유지한다.

## 구현된 흐름

- 수집 계정에 로그인하고 자동 제출 안내를 확인한 뒤 정산 등록하면 원본 파일과 별도 마킹 PNG, 보상 기록을 IndexedDB 트랜잭션에 함께 저장한다.
- 대기열이 `collect` 서버의 begin → 서명된 비공개 업로드 → finalize를 호출한다. 실패는 같은 UUID로 재시도한다. 브라우저를 닫으면 중단되며 다시 열 때 이어간다.
- 서버는 `auth.getUser(token)`으로 사용자 JWT를 검증한다. owner_id는 클라이언트 입력을 받지 않는다. 서비스 키는 Supabase 서버 기본 환경변수에만 있다.
- 서버가 정리한 payload 해시를 이용한 멱등성, 이미지 바이트 수/해시/파일 헤더/해상도 검증, 소유자별 상태/철회, 관리자 명부 검사, 검토 이력을 구현했다.
- 단가/참여자 이름/메모/파일명은 수집 payload에 포함하지 않는다. 원본 이미지 안의 닉네임은 포함될 수 있다.
- 저장소는 `raid-evidence` 비공개 버킷이다. 직접 테이블 접근은 권한 회수 + RLS로 막고 관리자 이미지 조회는 5분짜리 서명 URL을 발급한다.
- 관리자 수집함은 100건씩 보스/검토 상태로 조회하고 원본·마킹 이미지, 인식값, 동일 원본 해시 기록 수, 검토 이력을 표시한다. CSV는 현재 조회한 페이지를 내보낸다.
- 정산 등록/삭제와 제출/철회 대기열 저장은 같은 IndexedDB 트랜잭션이다. 기존 localStorage 장부는 첫 실행에서 이관한다. 과거 기록과 JSON 복원 기록은 자동 제출하지 않는다.
- 로컬 모드의 수동 기록, 로그인 전 기록에는 중앙 제출이 없다. 완료된 제출은 로컬 대기열 이미지 Blob을 비운다. JSON 백업에는 이미지와 대기열이 없다.

## 일반 사용자 공개 전에 필요한 설정

Supabase 기본 SMTP는 프로젝트 팀의 사전 승인 이메일만 지원한다. 일반 사용자 회원가입을 열려면 별도 SMTP 설정 또는 OAuth 공급자 설정이 필요하다. 이메일 인증을 꺼서 우회하지 않는다.

공식 문서: https://supabase.com/docs/guides/auth/auth-smtp

SMTP 비밀번호, Supabase 서버 비밀 키, OAuth 클라이언트 비밀 값은 저장소나 채팅에 넣지 않는다. 공급자 설정은 대시보드에서 직접 처리한다.

## 실제 확인과 한계

- 로컬 테스트: 실제 카드 OCR, 참여자/보상 수정, 기존 장부 이관, 실패 재시도, 동일 UUID, 개인정보 필드 제외, 이미지 Blob 정리, 삭제 철회, 서버 JWT/소유자/관리자 경계.
- 배포 서버: 인증 없는 요청 차단, 직접 테이블 읽기 차단, 공개 이미지 접근 차단.
- 앱 계정 및 관리자 명부 설정 후 실제 두 계정으로 업로드→관리자 조회→철회 검증을 완료해야 한다. 모의 네트워크 테스트만으로 실제 업로드를 완료했다고 판단하지 않는다.
- 90일 자동 보관/24시간 미완료 파일 정리 스케줄, 정정 revision, 전체 DB 내보내기, 설치형 전송은 아직 구현하지 않았다. 설계 문서의 해당 항목은 후속 작업이다. 운영 전에 보관 정책과 정리 작업을 구성해야 한다.
- 서버 이미지 확인은 파일 헤더/크기/해시/해상도를 검사한다. 전체 픽셀 디코딩이나 원본의 게임 진위 판별은 하지 않는다.
- 브라우저 자동 삭제/비공개 모드에서는 로컬 데이터가 사라질 수 있다. 장부 JSON 백업을 보관한다.
